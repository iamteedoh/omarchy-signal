# Security Policy

## Reporting a vulnerability

**Do not report security vulnerabilities through public GitHub issues.**

Use GitHub's private vulnerability reporting instead:

1. Open the repository's **Security** tab.
2. Select **Report a vulnerability**.
3. Provide the details requested below.

If private reporting is unavailable, contact the maintainer through the
[iamteedoh GitHub profile](https://github.com/iamteedoh).

### What to include

- A description of the issue and its potential impact
- Reproduction steps or a minimal proof of concept (a crafted message,
  contact name, attachment or socket request is ideal)
- The affected release, commit, Omarchy version and terminal
- A suggested remediation, if known

Never include live tokens, your `signal-cli` data directory, message
history, phone numbers or unredacted logs in a report.

### Supported versions

Security fixes land on `main` and ship in the next tagged release. Test
against the latest release or `main` before reporting an issue.

## What this project is, cryptographically

Nothing. All Signal protocol work (X3DH/PQXDH key agreement, Double Ratchet,
sealed sender, safety numbers, attachment encryption) happens inside
`signal-cli`, which links Signal's own `libsignal`. omarchy-signal never
sees a key, never touches ciphertext, and never talks to Signal's servers. It
talks to `signal-cli` over a private stdio pipe and to its own clients over a
private Unix socket.

If you want to audit the encryption, audit `libsignal` and `signal-cli`. If
you want to audit omarchy-signal, the interesting question is: *can a message
from a stranger, or another local process, make this software do something
the user did not ask for?*

## Threat model

Attackers considered:

1. **A remote sender** (anyone who can message you on Signal) controlling
   message bodies, names, group titles, attachment names and types, quotes,
   reactions, mentions and URLs.
2. **Another local user or process** with access to `/tmp`, `/run`, or
   D-Bus, but not to your uid.
3. **A malicious or buggy client** of the bridge socket (same uid).

Not considered: an attacker with your uid on your machine (they can read
`signal-cli`'s key store directly, as with Signal Desktop), a compromised
`signal-cli`, or a compromised Omarchy shell (plugins run unsandboxed inside
it by design).

## Defences

### Terminal injection (remote sender → terminal client)

Text is sanitised in `lib/omarchy_signal/sanitize.py` (`clean_text`) before
it is stored, again before it is sent to a client, and the same rules run in
`Model.js` for the Quickshell surfaces:

- every C0 and C1 control character is removed except newline and tab
  (tab becomes spaces), so ESC, CSI, OSC, DCS, APC, BEL and ST can never be
  spliced into our own escape sequences (title changes, OSC 52 clipboard
  writes, OSC 8 links, kitty graphics commands, cursor moves, screen clears,
  DA/CPR queries that echo into input);
- Unicode format characters (bidi overrides and isolates, BOM, soft hyphen),
  lone surrogates, private-use code points (Nerd Font glyphs live there and
  could impersonate our UI) and unassigned code points are removed;
- text is NFC-normalised and length-capped.

Links are only ever generated by us: URLs are found with a strict regex,
restricted to `http`, `https` and `mailto`, percent-encoded into the OSC 8
safe character set and length-capped (`links.py`). `file://` links point only
at attachment paths the bridge resolved inside `signal-cli`'s attachment
directory. `xdg-open` is invoked with an argv array.

Every Quickshell `Text` is `Text.PlainText`; nothing from the network is
rendered as rich text or markup.

### Images (remote sender → image decoder)

Dimensions are read from file headers without decoding. Anything over 40 Mpx
is refused. Non-PNG images are converted by ImageMagick in a subprocess with
memory, map, time and dimension limits and `-strip` (EXIF/GPS is dropped
before the bytes reach the terminal). PNGs that are already small are passed
through without any decoder running. The kitty protocol is used in quiet mode
(`q=2`) so the terminal never answers into our input stream.

### Command injection (any input → subprocess)

No shell strings carry remote data. `signal-cli` is invoked with an argv list
and driven over JSON-RPC; the single shell string in the code base is the
launch command handed to Omarchy's `omarchy-launch-or-focus` (which evals
it), assembled from our own fixed argv with `shlex.quote` and never from
message text. The Quickshell plugin does not go through a command line for
messages at all: it is a client of the bridge's socket (`Bridge.qml`), and a
send, reaction or delete is a JSON request built by `Model.requestLine` with
`JSON.stringify`, which the bridge validates against its schema like any other
client's. A parameter cannot replace a request's `id` or `op`, and message text
cannot start a second request, because a newline inside a JSON string is
escaped. The few programs the plugin still starts (the terminal client, the
file listing for the attachment picker, reading the clipboard, window
placement, the update check) go through `execArgv` or `BoundedProcess.qml`
with an argv array, and `Model.tuiArgv` validates the conversation key against
`^(number|uuid|group|username):[A-Za-z0-9+/=_.-]+$` first.

### Output from other programs

What a helper prints is read with a ceiling and one deadline for the whole
run, counted as it arrives, and the helper is killed past either. In the shell,
`BoundedProcess.qml` does this for every process the plugin starts, reports
exactly once (also when a process cannot start), and drops a result whose
question has changed in the meantime. In Python, `bounded.py` does it for the
programs whose output comes from somewhere else: `wl-paste` (the clipboard's
owner), `git ls-remote` (the remote), and ImageMagick (a picture somebody
sent). Each runs in a session of its own and its whole process group is
killed.

### Clipboard

Qt reads a clipboard offer whole, on the GUI thread, with no size or time
limit, and an editable text field does it by itself whenever the clipboard
changes (to update `canPaste`). Every native text field in the plugin is
therefore read-only unless it has keyboard focus and is on screen
(`PasteGuard.qml`), which also means its window is the active one. It has no
context menu. `Ctrl+V`, `Shift+Insert`, `Ctrl+Shift+V`, the Paste key, the
right click and the middle click paste through `omarchy-signal paste`, which
reads through `wl-paste` with the limits above (60 000 characters of text,
3 s; 100 MiB for a picture, 8 s). A paste that arrives after the field was
edited, lost focus or was hidden is dropped. Checked in a nested Hyprland with
a 20 MB text offer delivered to the shell: an unguarded field made one
`wl_data_offer.receive` and grew the shell by 26 MB; with the guard, none.

While a field has focus, Qt still reads the offer when the clipboard
changes: that is inside Qt and needs a Qt with the formats-only `canPaste`
fix to go away.

### Installing and updating

`install.sh` installs packages only through Omarchy's `omarchy-pkg-add` and
`omarchy-pkg-aur-add`, after asking. It never calls `sudo` or a package manager
itself.

The plugin never downloads, checks out or runs new code by itself. Once a day
at most it lists the release tags on the git remote it was added from (and
sends nothing else; `update_check = false` turns it off), and when there is a
newer one it says so. Installing it is Omarchy's own `omarchy plugin update
iamteedoh.signal`, which shows the changes and asks first; `omarchy-signal
update` and the popup's Update button only start that command. Afterwards the
plugin refreshes its own unit, hook and keybinding block from the files Omarchy
put in place, and restarts a bridge that is running; it never starts, enables
or unmasks one that is not.

Recipients are allow-listed (`classify_recipient`): E.164, UUID, base64
group id, or Signal username. Nothing starting with `-` can reach
`signal-cli`'s argument parser (and in JSON-RPC mode there is no argv anyway).

### File access (client → bridge → filesystem)

Attachments to send are resolved with symlinks followed and must be regular,
readable, non-empty files ≤ 100 MiB under `$HOME` (the bridge has a private `/tmp`)
(`safe_attachment_path`). `/etc/shadow`, `/proc/self/environ`, FIFOs and
device nodes are refused. Remote attachment file names are reduced to a safe
basename (`safe_filename`) and are never used to write files: `signal-cli`
stores attachments under their opaque id.

### Local socket (other local processes → bridge)

The socket lives in `$XDG_RUNTIME_DIR/omarchy-signal/` (mode 0700) as
`bridge.sock` (mode 0600). Each connection is checked with `SO_PEERCRED` and
dropped if the peer uid differs. It works the other way too: the CLI and the
terminal client only connect when the directory is a real directory owned by
this user that nobody else can enter, and drop the connection unless the
process serving the socket runs as this user (`SO_PEERCRED` again), before
anything is sent. With `XDG_RUNTIME_DIR` unset (some cron and ssh sessions) the
directory is `/run/user/<uid>` when that is private, and otherwise
`~/.local/state/omarchy-signal/run`; never a shared path like `/tmp`, where
another local user could create it first. Requests are newline JSON with a 1 MiB
limit; each op has a parameter schema (`protocol.OPS`) and unknown ops or
wrong types are rejected before any handler runs. A second bridge refuses to
start on a live socket.

### Data at rest

- Message history: `~/.local/share/omarchy-signal/history.sqlite3`, created
  0600 in a 0700 directory. Plaintext, like `signal-cli`'s own key store next
  to it. Disable with `history_enabled = false` or bound it with
  `history_retain_days`.
- Disappearing messages are deleted when their timer runs out, as in Signal:
  the timer starts when a message is sent, or when it is read. It is hidden
  from every query the moment it expires; the bridge then deletes the row, the
  picture or file `signal-cli` downloaded for it, and its text in the
  conversation list's preview, and tells the clients to take it off screen.
  Messages stored before this was enforced (0.5.0 and older) start their timer
  when the bridge is upgraded.
- Attachments: `~/.local/share/signal-cli/attachments/`, chmod 0600/0700 by
  the bridge when it locates them.
- Logs: the bridge's own log lines never contain message bodies, names,
  numbers or file names, at any log level. Two qualifications:
  - Under the systemd user unit the logs go to **journald**, not to a file:
    `setup_logging` picks stderr whenever `INVOCATION_ID` is set. The
    `0600` file at `~/.local/state/omarchy-signal/` is used only when the
    bridge is run outside systemd. journald's user-unit logs are readable by
    you and by root.
  - `log_level = "debug"` also passes `--verbose` to `signal-cli` and records
    that process's stderr. That output belongs to `signal-cli`, not to this
    project, and is not filtered here, so the guarantee above covers our own
    lines only. `debug` is for troubleshooting, not for everyday use.
- `signal-cli` runs with `--trust-new-identities on-first-use` by default,
  the same policy as official clients; set `never` to hard-fail on safety
  number changes.

### Service hardening

The systemd unit runs with `NoNewPrivileges`, `ProtectSystem=strict`,
`ProtectHome=read-only` plus explicit `ReadWritePaths`, `PrivateTmp`,
`RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6`, `UMask=0077`, and the
usual kernel/cgroup protections.

## Known limitations

- The Omarchy shell has no sandbox for plugins; the plugin therefore keeps
  its logic minimal and delegates to the CLI.
- `history_enabled` stores plaintext on disk; full-disk encryption is the
  intended protection, as with Signal Desktop's database.
- Contact and group names are shown as sent by the remote party after
  sanitising; a contact can still pick a name that *looks like* someone else.
  Safety numbers are the answer to that and are managed in `signal-cli`.

## Reporting

This repository is private for now; report issues to the maintainer directly.
Please do not post message contents or safety numbers in a report.

## Test coverage for the above

`make security` runs the adversarial subset: a corpus of terminal-injection
payloads (`tests/python/test_sanitize.py::INJECTIONS`), hostile envelope
shapes, option-injection recipients, path traversal and device-node
attachments, oversize and malformed socket requests, socket and database
permissions, the request builders in `Model.js`, and the updater (`tests/python/test_update.py`, `test_sync.py`).
