# Contributing to omarchy-signal

Thanks for helping improve omarchy-signal. This guide covers local setup,
validation, and the pull request process.

## Ways to contribute

- **Report a bug** using the repository's bug report form.
- **Request a feature** using the feature request form.
- **Send a pull request** after opening an issue for non-trivial changes.
- **Report a vulnerability privately** by following [SECURITY.md](SECURITY.md).

## Prerequisites

- Omarchy 4.x (Quattro) for anything that touches the shell plugin
- Python 3.11 or newer (the tests run on 3.12 in CI)
- Node.js 20 or newer (tests for `Model.js`)
- `qrencode` and ImageMagick (used by a few tests)
- gitleaks 8.30.1 or newer

`signal-cli` is **not** needed to run the test suite: the integration tests
drive the bridge with `tests/python/fake_signal_cli.py`.

## Set up from a clean clone

```bash
git clone https://github.com/iamteedoh/omarchy-signal.git
cd omarchy-signal
make test
```

To try a change on your own desktop, `./install.sh --no-bind --no-menu`
copies the checkout into `~/.config/omarchy/plugins/iamteedoh.signal` and
restarts the bridge and the shell. Do not symlink a checkout into the
plugins directory; every save would reload the shell.

Never commit secrets, tokens, phone numbers, message history, your
`signal-cli` data directory, or values specific to your own machine.

## Run the validation suite

Run the same checks that protect `main`:

```bash
make python        # unit + integration tests against the fake signal-cli
make qml           # node tests for Model.js
make bash          # static checks: syntax, systemd unit, manifest, QML hygiene
make qmlcheck      # loads Service.qml in a throwaway Quickshell (needs Omarchy)
make security      # the adversarial subset
gitleaks git . --config .gitleaks.toml --redact --no-banner
```

Anything visual (the terminal client, the popups, the chat window) should be
checked on a real Omarchy desktop before it is called done; `scripts/demo-env.sh`
gives you a bridge with fictional contacts so you never test against your own
account.

## Project layout

- `manifest.json`, `Service.qml`, `BarWidget.qml`, `ConversationView.qml`,
  `Model.js`, `Emoji.js`: the Quickshell plugin (`Emoji.js` is generated by
  `scripts/gen_emoji_js.py`)
- `bin/omarchy-signal`, `lib/omarchy_signal/`: CLI, terminal client and the
  bridge daemon (`bridge.py`, `rpc.py`, `protocol.py`, `store.py`, `sanitize.py`)
- `systemd/`: the user service unit
- `install.sh`, `uninstall.sh`, `scripts/`: installer, post-update hook, demo
  and generator scripts
- `tests/`: Python, node and bash suites
- `docs/`: status notes and the generated `config.example.toml`
- `.github/workflows/`: validation and source-only release automation

## Pull request process

1. Create a branch from `main`.
2. Make the smallest complete change and update documentation.
3. Run the full validation suite above.
4. Use a [Conventional Commit](https://www.conventionalcommits.org/) PR title:
   `feat:`, `fix:`, `docs:`, `refactor:`, `ci:`, `test:`, or `chore:`.
5. Complete the pull request template and link the related public issue.
6. Wait for all required checks to pass, then squash-merge.

The PR title becomes the squash commit subject and drives release-please:
`fix:` creates a patch release, `feat:` creates a minor release, and a `!` or
`BREAKING CHANGE:` footer creates a breaking release.

### A pull request that does more than one thing

Because every merge is a squash, the PR title is the only commit that reaches
`main` — so a PR normally contributes exactly **one** line to the release notes,
however much it contains.

When a PR carries several distinct changes, list them in an override block in
the **PR body** and release-please will use those lines instead of the title:

```
BEGIN_COMMIT_OVERRIDE
fix: keep the installer from truncating bindings.lua
fix: keep the installer from corrupting the Omarchy menu
test: run the installer end to end against a sandbox HOME
END_COMMIT_OVERRIDE
```

Each line is an ordinary Conventional Commit and lands in its own section. The
block only works with a squash merge, which is what this repository does.

**The opening marker must appear exactly once in the body.** release-please takes
the *first* occurrence as the start of the block, so a PR that also mentions the
marker in prose — while explaining this very mechanism, say — makes it swallow
the prose in between and try to parse list bullets as commits. Describe it as
"the override block" rather than spelling the marker a second time.

That failure is silent: release-please still exits 0 and the release proceeds.
The symptoms are a changelog that is thinner than the work that landed, and a
line in the release-please run log reading:

```
commit could not be parsed: <sha> <the PR title>
error message: Error: unexpected token ' ' at 1:2, valid tokens [(, !, :]
```

followed by a `Considering: N commits` count lower than expected.

To repair it, edit the merged PR's body so the marker appears once, then re-run
the workflow:

```
gh run rerun "$(gh run list --workflow=release-please.yml --limit 1 --json databaseId -q '.[0].databaseId')"
```

This works on an already-merged PR as long as the release PR has not been merged
yet, and it is how the v0.4.2 notes were corrected.

## Releases

release-please watches `main`. After a releasable commit lands it opens (or
updates) a PR titled `chore(main): release X.Y.Z` that bumps `version` in
`manifest.json`, updates `CHANGELOG.md` and `.release-please-manifest.json`.
Merging that PR creates the `vX.Y.Z` tag and the GitHub Release.

`changelog-sections` in `release-please-config.json` decides what appears in the
notes. Release-please hides most types by default — only `feat`, `fix`, `perf`
and `revert` would show — so every type this project uses is listed there
explicitly with `hidden: false`. Only `chore` stays hidden, because
release-please's own `chore(main): release X.Y.Z` commits would otherwise appear
in the notes.

One consequence is deliberate: release-please treats a visible type as
*releasable*, so a `docs:`-only or `ci:`-only PR can open a release PR and bump
the patch version. There is no way to show a type in the notes without making it
releasable, and complete notes are worth the occasional extra patch release.

GitHub does not run workflows on pull requests opened by the Actions token,
so a fresh release PR shows no checks and the protected branch refuses it.
Close and reopen it (`gh pr close N && gh pr reopen N`); CI then runs and the
PR becomes mergeable. Nothing is built or uploaded: users install from the
repository with `omarchy plugin add`, which clones the current `main`.
